# 步骤 8：自建一个"类 Jev"决策模型的可行性

> 日期：2026-09-22
> 前置：`05-jev-vs-qwen.md`、`06-laya-vs-jev.md`

---

## 一、结论先行

**能做，而且现在是最容易的时候 —— 但你大概率不该从训模型开始。**

三句话：

1. **架构不是护城河了。** Laya 用 421M 的 ModernBERT + 决策头，在 Jev 发布 3 天后开源了全部权重和训练配方（Apache 2.0）。可以直接读、直接抄。
2. **护城河是数据，不是模型。** Laya 零样本只有 0.362（低于 0.461 的多数类基线），0.766 是微调出来的。**通用零样本能力来自海量多样化的标注决策数据，这才是 TypeSafe 真正砸钱的地方。**
3. **但你大概率不需要通用模型。** 你需要的是"**在你那几十个问题上表现好**"的模型 —— 这个目标比通用模型容易一到两个数量级，而且垂类微调打通用 API 是现实的。

## 二、四级阶梯

| 级别 | 做什么 | 工作量 | 你得到什么 | 你得不到什么 |
|---|---|---|---|---|
| **T0** | Qwen + 约束解码，输出枚举 + logprob | 周末 | 可跑通的接口、评测基线 | 校准（logprob 不可信） |
| **T1** | T0 + **post-hoc 温度缩放** | 1~2 周 | **可用的概率** ⭐ 性价比最高 | 精度提升（只修概率，不修准确率） |
| **T2** | 抄 Laya：encoder + option-marker 头 + 垂类微调 | 1~2 个月 | 自己领域上可能**超过** Jev | 跨领域零样本能力 |
| **T3** | 复刻 RLCD 通用模型 | 数月~不可行 | 通用零样本 | —— 数据规模是硬墙 |

**建议路径：T0 → T1 → 评估是否真的需要 T2。大多数项目停在 T1 就够了。**

---

## 三、T1 是全场性价比最高的一步（重点）

很多人不知道：**校准的绝大部分收益来自一道后处理工序，不需要重新训练。**

证据就在 Laya 自己的模型卡里：

| | 温度缩放前 ECE | 缩放后 ECE |
|---|---|---|
| 英文 | 0.466 | **0.081** |
| 多语言 | 0.314 | **0.106** |

**Laya 出厂也是过度自信的**，那个"3x better calibration than Jev"的战绩，是温度缩放做出来的，不是 RLCD 独力做出来的。

### 怎么做

1. 拿任意模型（Qwen / Laya base / 甚至 API）对每个选项拿到 logits 或 logprob
2. 留出一个人工标注的验证集
3. 学一个标量温度 `T`，最小化 NLL：`softmax(logits / T)`
4. **按 (题型, 选项数) 分组各学一个 `T`** —— Laya 就是这么分组的，因为不同选项数的过自信程度不同
5. 评估用 **ECE**（期望校准误差）+ 可靠性图，不要只看准确率

选项少时温度缩放够用；样本多时可以上 isotonic regression（更灵活但更容易过拟合）。

> **关键认知**：准确率和校准是两件独立的事。T1 不会让你的模型更准，但会让你的**阈值真正可信** —— 而 `docs/05` 里"该用 Jev"的第一条理由就是"代码要按概率分档"。T1 直接把这条理由还给了你自建的方案。

## 四、T2 的具体配方（Laya 已公开）

### 架构

```
输入:  [state] [SEP] [instructions] [选项1 [MASK]] [选项2 [MASK]] ... 
骨干:  双向编码器（ModernBERT-large / mmBERT-base；中文可换中文预训练 encoder）
头:    2 层 transformer + option-marker scorer + act/escalate 头
输出:  对每个 [MASK] 位置打分 → 按问题做 softmax → 概率分布
```

**核心机制是 option markers**：每个选项在**自己的 `[MASK]` 位置**上被打分。
这一招是全部关键 —— 它让 **schema 可以在请求时任意定义，新 schema 不需要重训**。没有它，你就退化成标签集焊死的传统分类器。

三个原语的落地：
- `choice`：N 个选项 → N 个 mask → softmax
- `noul`：2 个选项（是/否）→ 取"是"的概率
- `score`：有序等级 → 同样 N 个 mask，但**损失函数要换**（见下）

### 训练目标

Laya 公开的 RLCD 实现：

| 要素 | 做法 |
|---|---|
| 策略 | 输出一个分布 |
| 探索 | 给 logits 加零均值高斯噪声 |
| 奖励 | **严格适当评分规则**：log + spherical；序数题额外加 **RPS**（ranked probability score） |
| 优化 | REINFORCE + group-mean baseline |

> **严格适当评分规则**是校准的数学根源：这类损失的最优解**恰好是真实概率**，所以模型被逼着说实话，而不是被逼着说得好听（RLHF 的问题）。
> 序数题必须用 RPS 而不是普通交叉熵 —— 因为"把 3 级猜成 2 级"应该比"猜成 5 级"罚得轻，交叉熵不区分这个。

**简化版**：你其实不一定需要 RL。**直接用 proper scoring rule 做监督训练（soft target + log loss / Brier）就能拿到大部分校准收益**，实现难度低一个数量级。RL 那套是在没有 soft target 时的替代方案。

### 数据从哪来（这才是真正的工作量）

| 来源 | 做法 | 拿到什么 |
|---|---|---|
| **改造现成分类数据集** | 每个数据集 = 一个 schema，标签集 = 选项 | **schema 多样性**（零样本泛化的来源） |
| **从强模型蒸馏软标签** ⭐ | 对同一题采样大模型 N 次（带温度），**经验频率就是软目标** | 校准训练最想要的 soft target，不需要人标 |
| 你自己的业务标注 | 领域内真值 | 垂类精度 |

第二条是性价比最高的：**用采样频率当软目标 + proper scoring rule 训练**，这是一条绕开 RL 的现实路径。

### 算力

421M 参数的编码器微调，**单张 4090 / A100 量级就够**，数据几千到几万条。
这是个人和小团队完全承受得起的规模 —— **成本瓶颈是标注，不是算力。**

## 五、T3 为什么基本做不了

通用零样本能力 = 模型在**没见过的 schema** 上也能给出校准概率。

这需要训练时见过**极其多样**的 (state, question, answer) 三元组：领域要广、schema 形状要杂、答案要带概率信号而不只是硬标签。

Laya 的数字就是这堵墙的实测：**零样本 0.362 < 多数类基线 0.461**。
它架构对了、方法对了、骨干够好了，**唯独数据规模不够**，所以零样本不可用，必须微调。

**这说明架构可以抄，数据抄不了。**

## 六、最该避免的三个坑

### 坑 1：一上来就训模型 ⭐ 最常见

**先做评测集。**

没有评测集，你无法知道自研的东西是好是坏，也无法知道现成的够不够用。
而且 —— **评测集是整个项目里最有价值、最持久的资产：换模型它不变，换架构它不变，两年后它还在。** 模型会被淘汰，评测集不会。

评测集至少要有：
- 覆盖你真实分布的 state（包括长尾和边界）
- 每题的人工真值
- 足够画出 confidence-准确率曲线的样本量

### 坑 2：以为校准要靠训练

大部分校准收益来自 post-hoc 温度缩放（见第三节）。先做这个，再考虑改训练目标。

### 坑 3：把准确率和校准混为一谈

两个独立指标，要分开测：
- 准确率 → accuracy / F1
- 校准 → **ECE + 可靠性图**

一个 0.95 准确率但严重过自信的模型，在需要阈值分档的场景里可能不如 0.85 准确率但校准良好的模型。

## 七、给 JEV-Try 的建议路线

```
第 1 周   做评测集（中文，你的真实数据，人工标真值）      ← 别跳过
   ↓
第 2 周   跑 docs/06 第七节那个四方对照（Jev / 译英Jev / Qwen / Laya）
   ↓
分叉判断：现成方案够用吗？
   ├─ 够用    → 选一个用，结束。省下几个月
   └─ 不够用  → T1 温度缩放（1~2周）→ 再判断一次
                  ├─ 够用   → 结束
                  └─ 不够用 → T2 抄 Laya 架构 + 垂类微调
```

**每一个分叉点都可能让你省掉后面全部工作。按顺序走，不要跳级。**

### 自研真正说得通的三种情形

| 情形 | 为什么 |
|---|---|
| **中文 + 私有化 + 有标注数据** | Jev 中文弱、不能私有化、不能微调；Laya 零样本不可用但可微调 —— 这个交集正好是自研的甜区 |
| 问题集合稳定且数量有限 | 垂类微调的收益最大化，通用性的损失为零 |
| 调用量大到 API 成本压不住 | 自建的固定成本被摊薄 |

### 不该自研的情形

- 问题形状还在频繁变 → 零样本 API 的灵活性更值钱
- 没有标注数据也没预算标 → T2 以上全部无从谈起
- 团队没人做过模型训练和校准评估 → 隐性成本远超预期
