# 步骤 2：概念层与原语层调研

> 日期：2026-09-22
> 来源：docs.typesafe.ai（`introduction`、`concepts/system-one`、`concepts/state`、`primitives`、`confidence`、`introduction/machine-learning-primer`）

## 一、一句话结论

**Jev 不是更小更快的 LLM，它是一个"不产出文本、只产出带校准概率的类型化判断"的模型。**
它要替换的不是 ChatGPT，而是你代码里那段"写 prompt 让 LLM 返回 JSON，再解析、再兜底"的脆弱逻辑。

## 二、为什么会有这类模型（第一性原理）

| 层次 | RLHF（ChatGPT 路线） | RLVR（推理模型路线） | **RLCD（TypeSafe 路线）** |
|---|---|---|---|
| 优化目标 | 人类偏好的文本 | 可验证答案（数学/代码） | **校准的决策概率** |
| 输出 | 自然语言 | 自然语言 + 推理链 | **类型值 + 概率分布** |
| 副作用 | 谄媚、自信的幻觉、mode dropping | 慢、贵 | 不会写字、不会解释 |

TypeSafe 的核心判断（其 manifesto 的赌注）：**未来大规模自动化 ≈ 99% 机器对机器、1% 人机对话**。
所以机器接口比聊天接口更重要 —— 他们称之为 **Machine Native Intelligence**：让 AI 具备软件的属性（结构化、可靠、可观测、可测试、快、一致、便宜）。

**校准（calibration）的定义**：标为 0.2 的结果，长期看约 20% 为真；标 0.8 的约 80% 为真。
⚠️ 注意边界：**校准是群体统计性质，不保证任何单次回答正确**。

## 三、请求的三段结构

```
state（评估材料） + questions（若干判断） → answers（每题一个类型化答案）
```

### 3.1 state —— 要被评估的内容

- 类型：字符串 / JSON 对象 / 文本数组（**仅文本**，不支持图像、音频、视频）
- 心智模型：**你要交给一组专家做判断之前，先摆在他们桌上的材料**
- 推荐用**对象**：让每一部分有名字、关系清晰；只有单段文本的简单场景才用字符串
- 一个 state 可以同时装对话、订单、政策 —— 只要这个判断需要对照它们

### 3.2 questions —— 判断本身

每个 question = `ID` + `type` + `instructions` (+ `criteria`)

- **ID 是给代码用的，不会发给模型**。所以 `instructions` 必须自带完整语义，不能靠 ID 暗示。
- `instructions` 可以是 string / object / array。用对象时：一个字段放问题，其他字段放它引用的数据。
- 引用 state 里的字段用**反引号路径**：`` `ticket.messages[0].text` ``

### 3.3 三个原语

| 类型 | 回答什么 | 返回字段 | 适用 |
|---|---|---|---|
| **Choice** | 这些选项里选哪个 | `choice`、`probabilities`、`confidence` | 无序的已知集合：工单路由、文档分类、语言识别 |
| **Score** | 在有序等级上处于什么位置 | `score`、`legend`、`probabilities`、`confidence` | 连续谱且你能描述每一级：缺陷严重度、客户愤怒度、技能水平 |
| **Noul** | 这个陈述为真吗 | `noul`（0~1） | 干净的是非题，且概率本身就是有用信号 |

**关键约束（文档明确写死的）**：
- Choice 最多 **255 个选项**
- Score 至少 2 级，API 接受最多 **10 级**
- **Noul 没有 `confidence`**
- Choice/Score 的 `probabilities` 之和为 1；Score 的 `score` 是概率加权值，**可以落在两级之间**

### 3.4 最容易踩的语义坑

> **Noul = 0.5 不代表"中等程度"，而代表"是和否各一半可能"。**

问"这个候选人 Python 强吗"，0.5 是歧义的（"强"没定义）。
- 想量程度 → 用 Score，定义等级：无经验 / 有所接触 / 日常使用 / 深度专精
- 想要是非 → 把条件写死："简历是否声明候选人在工作中使用过 Python？"

## 四、组合规则（这是设计的真正难点）

### 4.1 同一 state 的独立问题，必须打包进一个请求

- 所有问题**并行评估、彼此隔离**（一个答案不会成为另一个问题的上下文）
- 加问题几乎不增加响应时间，只增加那几个问题的 token
- **因此"问一个可能用不上的问题"几乎免费** → 投机提问（Speculative fan-out）
- 官方 cookbook 数据：13 个问题打包成 1 次调用，比 13 次单独调用**便宜 12.2x、快 10.0x，答案不变**
  （注：`primitives.md` 页写的是 11.5x / 9.6x，`llms.txt` 索引写的是 12.2x / 10.0x，两处数字不一致，以 cookbook 正文为准，待步骤 4 核对）
- **副作用好处**：每题独立评估，所以加问题**不会产生 context rot**

### 4.2 什么时候才需要第二次请求

只有当**代码在拿到第一个答案之前根本构造不出第二个请求**时：
1. 需要用答案去拉取新数据放进 state
2. 需要用答案决定 state 由什么组成
3. 需要用答案决定下一题的选项集合

否则一律打包。**两次请求是例外，不是常态。**

### 4.3 复杂判断要拆

不要问"评价这份创业 pitch"，要拆成：市场规模、技术可行性、差异化 —— 三个 Score，然后**在代码里加权**。
收益：优先级变了改一个系数，而不是重写 prompt。这叫 **Composite scoring** 模式。

## 五、confidence 的正确用法

### 5.1 它是什么

`confidence` 是从 `probabilities` 分布**推导出来的统计量**（分布越尖 → 越高，越平 → 越低），范围 0~1。
TypeSafe 说这是"合理默认值"，但你永远拿得到完整 `probabilities`，可以自己换算法。

低 confidence 的含义：
- Choice：没有哪个选项明显胜出
- Score：等级定义歧义、多维度混杂，或 state 信息不够

### 5.2 三档路由模板

| 档位 | 系统行为 |
|---|---|
| 高 | 自动执行 |
| 中 | 谨慎执行：让用户确认 / 标记人工复核 / 补充信息 |
| 低 | 不要执行：转人工、要求澄清、回退到其他系统 |

### 5.3 阈值不是一个数，而是随风险分层

官方示例的精髓：**同一次判断，不同动作用不同阈值**。
- `confidence < 0.5` → 一律转人工（模型自称不确定）
- 只读操作（查余额）→ 过了 0.5 就直接做，错了也可恢复
- 破坏性操作（批准转账）→ 要 `> 0.9` 才带确认执行，否则先让用户核对

### 5.4 三条反直觉的告诫

1. **confidence 衡量的是分布集中度，不是"工作流正确性"，更不是"可以行动的许可"**
2. **多个都能接受的备选也会摊薄概率** —— 低置信不必然说明这次判断有问题（比如无害的偏好选择）
3. **用不到的分支上的不确定性，直接忽略**（投机提问的答案没走到，别管它的置信度）

## 六、对本项目的启示

1. 设计时先问"**代码最终要做什么动作**"，倒推需要哪些判断 —— 而不是先想"AI 能答什么"。
2. 已知规则、精确计算、查表、执行，**全部留在代码里**。只在需要语义理解的缝隙插判断。
3. 把**策略（权重、阈值、过滤）和原始判断分离**：证据和问题语义没变时，改权重不需要重新推理。
4. 类型化输出只保证**接口正确，不保证内容为真**。必须在自己的数据上验证。
