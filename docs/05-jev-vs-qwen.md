# 步骤 6：Jev 与 Qwen 小模型的任务分工

> 日期：2026-09-22
> Jev 侧依据：`docs/01~04` 已核实的线上文档
> Qwen 侧依据：开源小参数生成式模型的**类属性**（生成能力、可微调、可私有化、中文原生、多模态变体）。
> ⚠️ 具体型号选择、参数量、基准分数需要另行核实，本文不引用未经验证的数字。

---

## 〇、速查表

### 判据

| 判据 | → Jev | → Qwen 小模型 |
|---|---|---|
| 答案空间 | 封闭、可枚举（≤255 选项 / ≤10 级 / 是非） | 开放文本，候选难以枚举 |
| **代码是否消费不确定性** | 要拿概率分档、设阈值、排序 | 只要一个标签 |
| 判断跳数 | 一跳常识快判 | 多跳推理、长链条 |
| 语言 | 英文为主 | **中文为主**（Jev 的 CJK 准确率明确更低） |
| 部署 | 可以走云 API | 必须私有化 / 离线 / 数据不出境 |
| 模态 | 纯文本 | 有图像、音频 |
| 流量 | 低量 / 突发 / 无运维预算 | 高稳态吞吐，自建可摊薄 |
| 是否需要微调 | 不需要（Jev 不支持） | 有标注数据，想靠 LoRA 拉开差距 |

### 适合 Jev、不适合 Qwen 小模型

| # | 任务 | 典型例子 | 决定性理由 |
|---|---|---|---|
| 1 | **按概率分档的门控决策** ⭐ | 风控放行/复核/拦截三档、审核自动处置 vs 人工队列、高风险操作确认策略 | 要的**不是标签，是校准概率**。Jev 走 RLCD，标 0.8 长期约 80% 为真；小模型 logprob 经 SFT/RLHF 后过度自信且未校准，据此调的阈值会随分布漂移悄悄失效 |
| 2 | **一份大文档 × 多个维度** ⭐ | 合规检查清单、尽调问卷、简历多维打分、保险理赔多条款核对、财报多指标 | **结构性差异**：Jev 文档只 ingest 一次、N 个判断并行隔离、不产生 context rot；Qwen 要么重发 N 次（成本延迟 ×N），要么一个 prompt 塞 N 题（问题互相污染 + 位置偏差）。实测 54k 字符 + 13 题 = $0.000497 / 0.27s |
| 3 | **海量候选重排打分** | RAG 重排、搜索排序、推荐候选、182 skill 选 1、450 实体对判重 | 调用次数极多 × 单次判断极简单 × 要跨候选可比的分数。$0.042/Mtok 且输出免费，结果直接可排序。实测 CLERC top-1 5%→18% |
| 4 | **实时路径路由（<300ms）** | 语音助手意图识别、入口 handler 分流、turn 级工具选择 | Jev 不生成 token，一次前向出分布；小 Qwen 仍需逐 token 解码，自建还要算排队和冷启动 |
| 5 | **LLM 护栏与裁判** | 越狱检测、提示注入筛查、引用核查、工具调用参数校验、RAG 段落筛查 | 用同类生成模型当裁判有同源偏差、可能被同一注入一起攻破、自评过度自信。Jev 是不同训练路线 + 返回可阈值化概率（边界：Jev 也不免疫注入，只是更好） |
| 6 | **给传统 ML 造语义特征** | 购买意向、竞争压力、流失信号 → CatBoost / XGBoost | 特征质量取决于跨样本可比 + 稳定 + 便宜，校准直接决定前两点。未校准 logprob 当特征会把噪声带进下游 |
| 7 | **无运维预算 / 流量突发** | 没有 GPU、不想维护推理服务、尖峰明显 | 纯变动成本优于养常驻 GPU |

### 适合 Qwen 小模型、不适合 Jev

| # | 任务 | 典型例子 | 决定性理由 |
|---|---|---|---|
| 1 | **需要生成文本** ⭐ 硬边界 | 摘要、改写、翻译、回复草稿、代码/SQL 生成 | Jev 官方明说没被训练来生成文本，用 Choice 链硬凑又差又慢 |
| 2 | **中文为主的业务** ⭐ | 中文工单、中文合同、中文内容审核 | Jev 文档原文：英语是主训练语言，CJK「能处理但不同等」。**这一条权重高于其他所有技术判据** |
| 3 | **开放答案空间的抽取** | 抽"甲方全称"、自由格式项目描述、用户自述现象 | Jev 只能**从你给的候选里选**。候选能枚举它选得很好；候选本身难枚举它就无从下手 |
| 4 | **需要领域微调** | 行业术语、内部分类体系、独有判断标准 | Jev **不做 fine-tune / LoRA，全账号同一套权重**，天花板固定。LoRA 过的小 Qwen 优势随标注数据积累持续扩大 |
| 5 | **数据不能出境 / 离线** | 私有化部署、内网隔离、边缘设备 | ZDR 是"出去了但不留存"，不等于"没出去" |
| 6 | **多模态** | 截图理解、票据识别、音频 | Jev 纯文本，只接受 string / JSON object / 文本数组 |
| 7 | **多跳推理 / System Two** | 需要真正推理链、双重否定、属性的属性 | Jev 已知缺陷：间接引用与多跳明确掉准确率，且它**很字面**——拆不成单跳判断就别用 |
| 8 | **超长上下文** | 整本手册、超长会话历史 | Jev 硬限 64k/请求、state + 最长单题 ≤32k。分块恰好破坏它"一次 ingest 多判断"的核心优势 |
| 9 | **高吞吐稳态流量** | 稳定大流量的线上服务 | 自建 GPU 摊薄后单位成本可能更低，且无限流、无供应商依赖（Jev 文档明确警告限流可能无预告变化）。⚠️ 须算全 TCO |
| 10 | **任务形状未定型的探索期** | 还没想清要问什么 | Jev 要求先把答案空间定义清楚；先用 Qwen 探索，形状稳了再迁到 Jev 固化 |

### 两者都不该用的

| 任务 | 正解 |
|---|---|
| 数学、精确计算 | 写代码。小模型算术同样不可靠 |
| 计数（字符、词频、列表项） | 写代码；或代码遍历候选 + 每项一个 Noul + 自己求和 |
| 日期排序、间隔、窗口判断 | 抽取交给模型（Choice 枚举各部件 + "未说明"选项），**运算全在代码里** |
| 精确查表、已知规则 | 写代码 |

### 三个容易判断错的地方

| 误判 | 实情 |
|---|---|
| 「Qwen 也能用 grammar 强制输出 JSON 和枚举」 | 对，**结构**可以保证，这不是 Jev 的独有价值。差别在**概率是否校准**：代码只读 `label` → 两者差不多，按语言和部署选；代码要读 `probability` 分档 → 差距是本质的 |
| 「分类任务就该用 Jev」 | 分类不是判据，**是否消费不确定性**才是。只要标签 + 中文 + 想微调的分类任务，Qwen 更合适 |
| 「Jev 更便宜」 | 只在按 token 计价这个口径下成立。低流量/突发 Jev 赢；高稳态吞吐自建可能赢。要算 GPU + 电 + 运维人力的全 TCO |

### 组合用法（往往才是最优解）

| 组合 | 怎么配 | 出处 |
|---|---|---|
| **生成候选 → Jev 选** | Qwen / regex 抽候选值，Jev 挑正确的那个 | Jev 官方明确推荐 |
| **级联校验** | 便宜模型抽取 → Jev 逐字段校验（Noul，true = 有问题）→ 仅告警时升级给大模型 | SDE cascade |
| **Jev 路由 → Qwen 执行** | Jev 快速分类 + 置信度门控，分流给不同 Qwen 专家 | Intent Routing |
| **Jev 当 Qwen 的护栏** | 进出 Qwen 的消息都过一遍越狱/注入/危害评分 | LLM guardrails |
| **中文绕道**（需实测） | Qwen 把中文译成英文 → Jev 判断 | 推论，**必须先测翻译损失是否小于 CJK 损失** |

## 一、结论先行：三个判据

不要按"这是不是分类任务"来分。按下面三条：

| # | 判据 | → Jev | → Qwen 小模型 |
|---|---|---|---|
| 1 | **答案空间是否封闭** | 选项可枚举（≤255 个 Choice / ≤10 级 Score / 是非） | 答案是开放文本，候选难以枚举 |
| 2 | **代码是否要消费不确定性** | 要拿概率分档、设阈值、排序 | 只要一个标签，或根本不需要置信度 |
| 3 | **判断能否一跳完成** | 常识性快判，单跳 | 需要多跳推理、长链条 |

**再叠加四条现实约束**：语言（中文？）、部署（能否出境？）、模态（有图？）、流量形态（突发还是稳态高吞吐）。

> 对本项目最关键的一条：**Jev 官方明确 CJK 准确率低于英文，Qwen 中文原生。**
> 这一条可以单独推翻上面所有技术判据。

## 二、适合 Jev、不适合 Qwen 小模型的任务

### 2.1 代码要按概率分档的门控决策 ⭐ 最本质的一类

**例子**：风控放行/复核/拦截三档、内容审核自动处置 vs 人工队列、转账等高风险操作的确认策略。

**为什么 Jev**：这类任务真正要的**不是标签，是校准概率**。
Jev 走 RLCD 训练，标 0.8 的事长期约 80% 为真。小 Qwen 的 token logprob 经 SFT/RLHF 后普遍**过度自信且未校准** —— 你能拿到一个数，但那个数和真实正确率之间没有稳定映射，据此调出来的阈值在分布漂移时会悄悄失效。

> 反过来说：如果你的代码只用 `label`、从不看概率，这条判据不成立，Jev 的优势就少了一大半。

### 2.2 一份大文档 × 多个维度 ⭐ 结构性优势

**例子**：合规检查清单（一份政策文件核 N 条要求）、尽调问卷、简历多维打分、保险理赔对多条款、财报多指标提取。

**为什么 Jev**：这是**架构层面的差异，不是程度差异**。
- Jev：文档只 ingest 一次，N 个判断**并行且互相隔离** —— 加问题不产生 context rot
- Qwen：要么把文档重发 N 次（成本和延迟 ×N），要么一个 prompt 里塞 N 个问题 —— 此时问题之间会互相污染、后面的答案被前面的带偏、还有位置偏差

**实测锚点**：54,000 字符文档 + 13 道题，Jev 打包一次 = $0.000497 / 0.27s，比拆开调用便宜 12.2x、快 10.0x，**答案完全不变**（5 次重复大多 std dev 为 0）。

### 2.3 海量候选的重排与打分

**例子**：RAG 重排、搜索结果排序、推荐候选打分、182 个 skill 里选 1 个、450 个实体对判重。

**为什么 Jev**：调用次数极多 × 每次判断极简单 × 要的是**跨候选可比的分数**。
Jev 单价 $0.042/Mtok 且输出免费，输出直接就是可排序的数值。
实测：CLERC 法律检索 top-1 从 5% → 18%，top-10 从 38% → 62%。

### 2.4 实时路径上的路由（延迟预算 < 300ms）

**例子**：语音助手意图识别、请求入口决定走哪条 handler、聊天turn 级的工具选择。

**为什么 Jev**：Jev 不生成 token，一次前向就出分布。小 Qwen 即使很小也要逐 token 解码，自建服务还要算排队和冷启动。

### 2.5 给 LLM 当护栏和裁判

**例子**：越狱检测、提示注入筛查、引用核查、工具调用参数校验、RAG 段落相关性筛查。

**为什么 Jev**：用**另一个同类生成模型**当裁判有已知问题 —— 同源偏差、可能被同一个注入一起攻破、自评过度自信。Jev 是不同训练路线的模型，且返回可直接阈值化的概率。

> 注意边界：Jev 自己也**默认不把 state 当敌意内容**，注入仍可能带偏它。这是"更好"，不是"免疫"。

### 2.6 给传统 ML 模型造语义特征

**例子**：把"购买意向""竞争压力""流失信号"变成 0~1 数值，喂给 CatBoost / XGBoost。

**为什么 Jev**：特征质量取决于**跨样本可比 + 稳定 + 便宜**。校准直接决定了这三点。未校准的 logprob 当特征会把噪声带进下游模型。

### 2.7 没有运维预算 / 流量突发

没有 GPU、不想维护推理服务、流量尖峰明显 —— 纯变动成本的 API 优于养一台常驻 GPU。

## 三、适合 Qwen 小模型、不适合 Jev 的任务

### 3.1 任何需要生成文本的任务 ⭐ 硬边界

摘要、改写、翻译、回复草稿、代码生成、SQL 生成、报告撰写。
Jev 官方明说：**没有被训练来生成文本，用 Choice 链硬凑会又差又慢。**

### 3.2 中文为主的业务 ⭐ 对本项目最关键

Jev 文档原文：英语是主训练语言、准确率最好，**CJK 等其他语言"能处理但不同等"，依赖前请先在自己内容上测**。
Qwen 中文原生。**中文场景下这一条的权重高于本文所有其他判据。**

### 3.3 开放答案空间的抽取

**例子**：从合同里抽"甲方全称"、从简历抽自由格式的项目描述、从工单抽用户自述的问题现象。

**为什么不是 Jev**：Jev 只能**从你给出的候选里选**，选不了你没提供的值。
如果候选能用 regex / 解析器 / 生成模型先枚举出来，那 Jev 选得很好；**如果候选本身难以枚举，Jev 无从下手**。

### 3.4 需要领域微调

Jev **不做 fine-tune、不做 LoRA、不用客户数据训练，全账号共享同一套权重**。
有标注数据的垂类任务（特定行业术语、内部分类体系、独有的判断标准），LoRA 过的小 Qwen 常常能超过通用 API —— 而且这个优势会随标注数据积累持续扩大。

Jev 适配领域只有三条路：塞 state、写 criteria、代码里组合。天花板在那里。

### 3.5 数据不能出境 / 必须离线

私有化部署、内网隔离、边缘设备、合规要求数据不出机房。
（Jev 企业版有零数据保留 ZDR，但那仍然是"数据出去了但不留存"，不等于"数据没出去"。）

### 3.6 多模态

Jev **纯文本**：只接受 string / JSON object / 文本数组，不支持图像、音频、视频。
Qwen 有视觉语言变体。有图的任务直接出局 Jev（除非先用别的模型转成文本描述）。

### 3.7 多跳推理 / System Two 任务

Jev 官方已知缺陷列表明确：**间接引用、双重否定、属性的属性、多跳推理都会掉准确率**，且**它很字面**。
需要真正推理链的任务，要么用能推理的模型，要么你得先把它拆成多个单跳判断 —— 拆不动就别用。

### 3.8 数学、计数、日期运算

Jev 不是计算器、不会可靠计数（误差随规模增长）、把日期当文本不当有序量。
**但注意**：这类任务的正解通常既不是 Jev 也不是 Qwen，而是**写代码**。小模型做算术同样不可靠。

### 3.9 超长上下文

Jev 硬限：单请求 64k token，`state` + 最长单题 ≤ 32k。超过就得自己分块 —— 而分块恰恰会破坏"一次 ingest 多个判断"的核心优势。

### 3.10 高吞吐稳态流量

自建 GPU 是固定成本，流量够稳够大时单位成本可能低于 API，而且没有限流、没有供应商依赖（Jev 文档明确警告**限流可能无预告变化**）。
⚠️ 但必须算全 TCO：GPU + 电 + 运维人力 + 迭代成本。低流量或突发流量下自建几乎必输。

### 3.11 任务形状还没定型的探索期

Jev 要求你**先把答案空间定义清楚**（选项集合、等级描述）。还不知道要问什么的时候，生成模型的灵活性更值钱。先用 Qwen 探索，形状稳定后再迁到 Jev 固化。

## 四、三个容易判断错的灰色地带

### 4.1 "Qwen 也能用 grammar 强制输出 JSON 和枚举啊"

对，**结构**可以用约束解码保证，这不是 Jev 的独有价值。
真正的差别在**概率是否校准**：
- 你的代码只读 `label` → 两者差距不大，按语言和部署选
- 你的代码要读 `probability` 分档 → 差距是本质的，选 Jev

### 4.2 "分类任务就该用 Jev"

不对。**分类不是判据，"是否消费不确定性"才是判据。**
一个只要标签、中文、还想微调的分类任务，Qwen 更合适。

### 4.3 "Jev 更便宜"

只在**按 token 计价**这个口径下成立。真实对比要看：
| | Jev | 自建 Qwen |
|---|---|---|
| 成本结构 | 纯变动 | 固定（GPU）+ 运维人力 |
| 低流量/突发 | ✅ 赢 | ❌ 空转 |
| 高稳态吞吐 | 随量线性增长 | ✅ 摊薄后可能更低 |
| 限流风险 | ⚠️ 官方称可能无预告变化 | 自己说了算 |

## 六、给 JEV-Try 的行动建议

中文是本项目最大的不确定性。建议把它变成第一个要测的东西，而不是第一个要赌的东西：

| 方案 | 说明 |
|---|---|
| A. 中文直喂 Jev | 基线 |
| B. 中文 → Qwen 译成英文 → Jev | 测翻译损失 vs CJK 损失，哪个小 |
| C. 中文直喂 Qwen（约束解码出枚举） | 对照组 |

同一批中文数据、同一组判断、人工标注真值，比三件事：**准确率、置信度可用性（能否画出单调的 confidence-准确率曲线）、成本与延迟**。
这个对照实验本身就可以是 `docs/04` 里建议的那个「文档多维评估 CLI」的第一个功能。
