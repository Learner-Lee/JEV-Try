# 步骤 7：Laya 调研 —— "吊打 Jev"这个说法站不站得住

> 日期：2026-09-22
> 一手来源：HuggingFace 模型卡 `convaiinnovations/laya`、官网 `laya.convaiinnovations.com`
> 二手来源：若干独立评述（含对基准方法论的批评）
> ⚠️ Laya 于 **2026-09-18** 发布，距今 4 天；Jev 早它 3 天发布。**整个赛道不到两周，任何结论都短保质期。**

---

## 一、结论先行

**Laya 是个真东西，值得研究，但"吊打"不成立 —— 那张对比表不是同一条件下的比较。**

三句话：

1. **它确实在某些维度实打实地强**：自托管零 token 成本、Apache 2.0 开源权重、单问题 32.8ms（比 Jev 快 7~8 倍）、原生多语言。
2. **它的核心战绩有方法论问题**：0.766 vs 0.727 是**微调过的 Laya** 对**零样本的 Jev**，而且 Jev 那个数**不是作者自己跑的**，是从别处引用的、prompt 和样本都不同。
3. **两者的能力边界是错开的，不是替代关系**：**Laya 上下文 512~1024 token，Jev 是 64k。** 差 60 倍以上 —— Jev 最强的那个场景（一份大文档 × 多个维度），Laya 结构上就做不了。

## 二、Laya 是什么（一手事实）

| 项 | 内容 |
|---|---|
| 出品方 | Convai Innovations |
| 发布 | 2026-09-18，Apache 2.0 |
| 定位 | 开源、可自托管的 System 1 类型化决策模型 |
| 原语 | `choice` / `score` / `noul`（**连命名都跟 TypeSafe 一样**） |
| 训练方法 | **RLCD** —— 也跟 TypeSafe 同名 |
| 安装 | `pip install laya` |

### 三个 checkpoint

| checkpoint | 骨干 | 参数 | 上下文 | 用途 |
|---|---|---|---|---|
| `laya`（root） | ModernBERT-large | 421M（395M 骨干 + 决策头） | **512 token** | 英文 |
| `laya-multilingual` | mmBERT-base | 322M，22 层，256k 词表 | **1024**（编码器支持到 8k，带 RoPE） | 100+ 语言 |
| `laya-typed-decisions` | ModernBERT-large | — | 1024 | 针对四类工作流微调 |

### 架构机制（这部分很有参考价值）

- **双向编码器 + 决策头**：2 层 transformer + option-marker scorer + act/escalate 头
- **Option markers**：每个选项在**自己的 `[MASK]` 位置**上被打分，然后按问题做 softmax
- 因此 **schema 可以在请求时定义，新 schema 不需要重训** —— 一个 encoder 也能做到动态标签集
- **RLCD 的具体实现**（Laya 版）：策略输出一个分布；探索时给 logits 加零均值高斯噪声；奖励用**严格适当评分规则**（log + spherical，序数题另加 ranked probability score）；REINFORCE + group-mean baseline

> 这是目前能看到的对 RLCD 最具体的描述。**但这是 Laya 的实现，不等于 Jev 的实现** —— TypeSafe 从未公开细节。

### 校准

**模型出厂是过度自信的**，必须按 (题型, 选项数) 做温度缩放：
- 英文 ECE：0.466 → **0.081**
- 多语言 ECE：0.314 → **0.106**

→ 工程含义：**校准不是白送的，是你要用留出集自己做的一道工序。**

## 三、"吊打"这个说法的三处硬伤

官方对比表：

| 指标 | Jev | Laya |
|---|---|---|
| typed-decisions 准确率（2000 条） | 0.727 | **0.766** |
| ECE（温度缩放后） | 0.246 | **0.081** |
| p50 延迟（单问题） | 236–276 ms | **32.8 ms** |
| AG News（4 类） | 0.910 | **0.950** |
| DAIR Emotion（6 类） | 0.480 | **0.595** |
| **Banking77（77 类）** | **0.870** | **0.425** ← 反向 |

### 硬伤 1：微调过的 Laya vs 零样本的 Jev ⭐ 最致命

Laya 自己的限制章节写着：**base checkpoint 在 typed-decisions 上零样本只有 0.362，而多数类基线是 0.461 —— 连蒙都不如。**
那个 0.766 属于 `laya-typed-decisions`，**是在这个基准自己的训练集上微调出来的**。

> Jev 是当零样本 API 卖的；Laya 老实讲是"一个你要去特化的底座"。**这两个数根本不在一个条件下。**

### 硬伤 2：Jev 的数字不是作者跑的

独立评述指出：**对比表里 jev-1.13.0 的成绩是从另一份已发表的评测里引用的**，Laya 作者在那轮里并没有实际调用 Jev，**prompt 和样本都不一样**。

### 硬伤 3：延迟不是同口径

32.8ms = 多语言 checkpoint、**单问题**、**本地 T4 GPU**、不含网络。
Jev 的 236–276ms = 托管 API，含网络往返、可能含冷启动和并发排队。

**这不是"模型快 7 倍"，是"本地推理 vs 跨网 API"。** 真要比模型本身，得把 Jev 也放本地 —— 而它不开源，比不了。

> 另外注意：Jev 官方实测 **54,000 字符文档 + 13 道题 = 0.27 秒**。跟这里引用的 236–276ms 量级一致，说明 Jev 的延迟**几乎不随问题数增长**；Laya 则是 1 题 32.8ms → 10 题 72.3ms，**随问题数上升**。

### Laya 官方自己承认的局限（这点值得加分）

- Choice 超过 20 个选项就开始退化；Banking77（77 类）只有 0.425 —— 默认设置下每个标签只分到 3~4 个 token
- base 模型在 typed-decisions 上约 0.35，"接近随机"
- **`score` 是最弱的原语**（SST-5 只有 0.372）
- 必须做温度校准

**能力边界写得这么坦白，是项目可信度的加分项** —— 问题出在传播环节，不在作者。

## 四、真实的能力边界对比

| 维度 | Jev (1.13) | Laya | 谁赢 |
|---|---|---|---|
| **上下文** | **64k / 请求**（state + 最长单题 ≤32k） | **512（英文）/ 1024（多语言，编码器到 8k）** | **Jev，压倒性** |
| 大文档 × 多维度 | 一次 ingest，N 题并行隔离 | **装不下文档** | **Jev（Laya 出局）** |
| 高基数 Choice | Banking77 0.870；支持 255 选项 | 20 选项以上退化，Banking77 0.425 | **Jev** |
| 低基数 Choice | AG News 0.910 | AG News 0.950 | Laya（但条件存疑） |
| score 原语 | Score 是一等公民（2~10 级） | **最弱原语**，SST-5 0.372 | **Jev** |
| 开箱校准 | 训练目标即校准 | **出厂过度自信，须自己温度缩放** | **Jev** |
| 校准后 ECE | 0.246 | 0.081 | Laya（条件存疑） |
| 单问题延迟 | 236–276ms（含网络） | 32.8ms（本地 T4） | Laya（口径不同） |
| 多问题延迟 | 几乎不随问题数增长 | 随问题数上升 | **Jev** |
| 中文 | 明确弱（CJK"能处理但不同等"） | 多语言 checkpoint，100+ 语言 | **Laya（但需实测）** |
| **可微调** | **不可能**（全账号同权重） | **可以，而且是推荐用法** | **Laya** |
| 私有化/离线 | 不行（企业版仅 ZDR） | **完全可以** | **Laya** |
| 成本结构 | $0.042/Mtok，纯变动 | $0 token 费，但要 GPU + 运维 | 看流量形态 |
| 运维负担 | 零 | 要养 GPU、做校准、管 checkpoint 路由 | **Jev** |
| 零样本可用性 | 卖点就是零样本 | **零样本≈随机，必须微调** | **Jev** |

### 一句话概括

> **Jev 是"开箱即用的通用判断 API"，Laya 是"你要自己特化的快速底座"。**
> 它们在同一个品类里，但卖的是完全不同的东西。

## 五、对之前结论的两处更正

### 更正 1：我说过"BERT 做不到请求时定义任意标签集" —— 这话说过头了

Laya 用 **option markers（每个选项在自己的 `[MASK]` 上打分）** 证明了：**编码器架构完全可以做动态 schema。**
这个论据作废。

但**关于 Jev 不是 BERT 的结论仍然成立**，其余四条证据没受影响：
64k 上下文（BERT 系原生 512，Laya 也正好卡在 512）、官方训练路线图把它放在"预训练语言模型 → RLHF/RLVR/RLCD"分叉上、文档自称"Like an LLM"、响应里有 `output_tokens`、以及一整套 LLM 式失败模式。

**而且 Laya 的 512 token 反过来印证了这一点**：ModernBERT 骨干就是这个量级，Jev 的 64k 不可能出自同类架构。

### 更正 2：你最初猜"是 BERT 吧" —— 在 Laya 身上你猜对了

Laya = **ModernBERT-large 骨干 + 决策头**，421M 参数。
这个直觉放在 Jev 上不对，放在 Laya 上完全正确。

## 六、Laya 怎么改变 `docs/05` 那张 Jev vs Qwen 的表

Laya 插在两者中间，**专门吃掉"Qwen 侧"里那几条与生成无关的理由**：

| docs/05 里"该用 Qwen"的理由 | Laya 是否也能满足 |
|---|---|
| 中文为主 | ✅ 多语言 checkpoint（需实测） |
| 数据不能出境 / 离线 | ✅ 自托管 |
| 需要领域微调 | ✅ 而且是推荐用法 |
| 高稳态吞吐省钱 | ✅ 单 T4 批量 103–332 问题/秒 |
| 需要生成文本 | ❌ 跟 Jev 一样不生成 |
| 多模态 | ❌ |
| 超长上下文 | ❌ **比 Jev 还差得多** |
| 多跳推理 | ❌ |

→ **如果你的任务是"类型化判断 + 中文 + 要私有化"，Laya 可能比 Qwen 小模型更对口** ——
因为它的输出契约天生就是类型化的，不需要靠约束解码去硬凑，而且概率经过校准（温度缩放后）。

## 七、必须自己验证的三件事

**不要信任何一方的官方数字，包括 Laya 的和 Jev 的。**

| # | 要验证什么 | 为什么不能信现成数字 |
|---|---|---|
| 1 | **中文到底行不行** | Laya 的多语言证据是"51 种语言里 45 种超过 3× random"。以 MASSIVE 的意图分类为例（约 60 个意图），3× random ≈ **5% 准确率** —— 这个门槛低到几乎不能说明可用性。**必须用自己的中文数据测。** |
| 2 | **零样本 vs 微调的真实差距** | 0.766 是微调出来的，0.362 是零样本。你有没有标注数据、能标多少，直接决定 Laya 对你是 0.77 还是 0.36 |
| 3 | **你的文档有多长** | 512/1024 token 是硬墙。中文一个字约占 1 个 token 上下，**1024 token ≈ 一千来字**。超过就只能分块，而分块会毁掉"一次 ingest 多判断"的全部优势 |

### 建议把 `docs/05` 第六节的对照实验扩成四方

| 方案 | 说明 |
|---|---|
| A | 中文直喂 Jev（基线） |
| B | 中文 → 译英 → Jev |
| C | 中文喂 Qwen 小模型（约束解码出枚举） |
| **D** | **中文喂 laya-multilingual（零样本 + 微调各一版）** |

同一批中文数据、同一组判断、人工标注真值，比四件事：**准确率、校准质量（ECE / confidence-准确率曲线是否单调）、成本、延迟**。

D 方案还要额外记一个数：**你的 state 有多少比例被 1024 token 截断。** 这个数如果高，Laya 直接出局，不用再比准确率。
