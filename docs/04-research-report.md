## 一、核心结论

**Jev 值得用，但用途窄而明确：它专门替换你代码里"让 LLM 返回 JSON 再解析"的那一段。**

三条支撑：

1. **它不是更便宜的 LLM，是另一类东西。** 不产出文本、不写代码、不对话，只产出**类型化判断 + 校准概率**。`model: "jev-latest"` 换不到一个 Jev 版的编码助手 —— 官方专门写了一页澄清这件事。
2. **经济性是数量级的，不是百分比的。** $0.042/百万输入 token，输出 token 免费。54,000 字符文档问 13 道题，一次调用 $0.000497、0.27 秒。这让"多问几道用不上的题"在成本和延迟上**都接近免费**，从而解锁了一种 LLM 做不到的架构：投机扇出。
3. **它的价值上限由你的问题设计决定，不由模型决定。** 模型不做 fine-tune、不用你的数据训练，全账号同一套权重。你唯一的杠杆是 state、instructions、criteria 和代码里的组合逻辑。

---

## 二、它解决什么问题（第一性原理）

LLM 被训练来产出**人类爱读的文本**（RLHF）。当你要它做一个**代码要消费的判断**时，存在根本错配：
你在把一个文本生成系统硬掰成结构化决策器，然后再把结果解析回来。

这个错配的代价是具体的：
- 需要写"请返回 JSON"的祈使句 prompt，并为它解析失败兜底
- 拿到的置信度是模型"说"出来的，不是校准出来的
- RLHF 奖励了**谄媚**和**听起来自信的幻觉** —— 对无人值守的自动化是致命的
- 加问题就是加上下文，会有 context rot

Jev 走的是第三条训练路线 **RLCD（强化学习优化校准决策）**：不生成文本，返回决策和概率，且**概率标 0.8 的事长期约 80% 为真**。

> ⚠️ 边界：**校准是群体统计性质，不保证任何单次回答正确。** 类型化输出只保证**接口**正确，不保证**内容**为真。

## 三、能力与代价一览

### 3.1 能力

| 维度 | 事实 |
|---|---|
| 三个原语 | Choice（选一个，≤255 选项）、Score（有序等级，2~10 级）、Noul（是非概率 0~1） |
| 并行 | 同一请求内所有问题**并行、隔离**评估；加问题几乎不增延迟，且**不产生 context rot** |
| 价格 | $42/Btok = **$0.042/Mtok**，仅计输入，输出免费 |
| 限流 | 250k tokens/s、1200 req/min（**官方声明可能无预告变化**） |
| 上下文 | 单请求 64k token；`state` + 最长单题 ≤ 32k |
| 接入 | 单端点 `POST /v1/systemone`；Python SDK（≥3.10）、JS SDK（Node ≥20），默认带退避重试 |

### 3.2 代价（jev-1.13 的九个锯齿）

按对我们的威胁排序：

| 风险 | 内容 | 缓解 |
|---|---|---|
| 🔴 **中文准确率** | **英语是主训练语言，CJK"能处理但不同等"** | **上线前必须用中文内容做对照测试**；中文场景更依赖 confidence 门控 |
| 🔴 **字面理解** | 它回答你写下的问题，不是你想问的。范围词、否定、隐含条件全按字面读 | 「当你看着错误答案想解释"我其实是想问…"，那句解释就是你缺的那半条指令」 |
| 🔴 **结构不变式不成立** | 同一问题用 Noul 得 0.22，用 yes/no Choice 得 yes=0.01；一个问题和它的否定两个 Noul 相加 = 1.19 | 别跨原语搬阈值；别指望算术恒等式 |
| 🟠 **数学/计数/日期** | 不会算数、不会可靠计数、把日期当文本 | 全部留在代码里。日期用 Choice 枚举各部件（留"未说明"选项），代码组装比较 |
| 🟠 **state 膨胀** | **Jev 有 context rot**，无关内容当干扰项，准确率随 state 变大下降 | **多问题、瘦 state**：先在代码里检索过滤 |
| 🟡 **对抗内容** | state 被当数据，**默认不视为敌意**；注入指令能带偏答案 | criteria 写死，上线前测边界 |
| 🟡 **别名漂移** | `jev-latest` 会指向新版本，阈值可能失效 | **钉死 `jev-1.13.0`**，日志记 `model` 字段 |

## 四、怎么用（工程范式）

### 4.1 设计顺序：从动作倒推判断

```
应用最终要做什么动作？  ← 从这里开始，不要从"AI 能答什么"开始
      ↓
这个动作需要哪些判断？
      ↓
每个判断选哪个原语？（按答案的形状选，不按问题的措辞选）
      ↓
哪些能打包进一次请求？（默认全部）
      ↓
代码怎么组合成动作？（策略和原始判断分离）
```

### 4.2 五条铁律

1. **已知规则、精确计算、查表、执行 —— 全部留在代码里。** 只在需要语义理解的缝隙插判断。
2. **同一 state 的独立问题一律打包。** 第二次请求只在"没有第一个答案就构造不出第二个请求"时才做（需要拉新数据、需要决定 state 组成、需要决定下一题选项）。
3. **复杂判断必须拆维度，权重放代码里。** 优先级变了改系数，不是重写 prompt。
4. **一个置信度下限兜底，每种动作按后果分别设阈值。** 只读操作宽松，破坏性操作严格。
5. **策略与原始判断分离。** 证据和问题语义没变时，改权重/改阈值/改展示过滤**不需要重新推理**。

### 4.3 两个高级技巧（来自 cookbook）

- **让 Score 的等级直接等于你的动作集合**（合并 / 不关联 / 人工），这样连阈值都不用调。
- **Choice 和 Noul 同请求配合**：Choice 回答"哪个最合适"（相对），Noul 回答"到底需不需要"（绝对，可以全低）。只用 Choice 会被迫必选一个。

## 五、对 JEV-Try 项目的建议

### 5.1 推荐的下一步：一个"最小但完整"的验证

不建议直接做 hello-world（学不到东西），也不建议直接上业务（风险未知）。建议做一个**同时验证三件事**的小项目：

| 要验证的 | 怎么验证 |
|---|---|
| 中文准确率到底损失多少 | 同一批内容，中英文各跑一遍，比对答案和 confidence 分布 |
| 打包 vs 单题的实际收益 | 在我们自己的数据上复现 parallel_questions 的对比 |
| 置信度阈值该定在哪 | 人工标注一小批，画 confidence-准确率曲线 |

**建议载体**：一个文档多维评估 CLI —— 输入若干文档，一次请求问多个维度（Choice + Score + Noul 混搭），输出结构化结果 + 成本/延迟统计。这正好是官方推荐给编码代理的起步项目形态，且天然覆盖上面三项验证。

### 5.2 立即可做的准备

- [ ] Playground 手工试几道题建立手感（`console.typesafe.ai/playground`）
- [ ] 申请 API key，写进环境变量 `TYPESAFE_API_KEY`（**不入库、不进前端**）
- [ ] 选语言栈（Python 生态更完整，有 async 客户端和 cooksafe 工具包；JS 有类型推断）
- [ ] 准备一小批我们自己的中文测试数据

### 5.3 什么时候**不要**用 Jev

- 需要生成文本、写代码、对话 → 用 LLM
- 答案需要精确数值、日期运算、计数 → 用代码
- 问题需要多跳推理 / System Two 思考 → 用推理模型，或拆成多个 System One 判断
- 一次性脚本、没有规模 → 直接调 LLM 更省事
